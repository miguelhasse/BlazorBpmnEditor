## 2. Source-of-Truth / State Ownership (**CONFIRMED**)

This determines almost every other design choice, so it is called out first.

**Confirmed model (hybrid, mirrors bpmn-js's approach):**

- **TypeScript owns the live interactive graph** (JointJS `dia.Graph` + semantic BPMN shadow model in `core/model`). All pointer-driven interaction — drag, connect, reconnect, resize, waypoint edit, stencil drop — happens entirely client-side for latency reasons, validated in real time using `core/validation` (§5.1 rule IDs: `SF-*`, `MF-*`, `CT-*`, `DI-*` subset).
- **Blazor/C# owns the document lifecycle and editor configuration**: import/export (via `Bpmn.Interchange`, see §3), structural/document-wide validation (§5.2–§5.5), property-panel-driven edits, stencil configuration, canvas/grid/snap settings, interaction options, theme/labels, routing options, keyboard map, contextual actions, accessibility options, export behavior, and persistence. C# resolves and validates defaults plus host overrides, then sends a versioned configuration snapshot to TypeScript before paper initialization and revisioned patches afterward. C# never manipulates the DOM/SVG directly — every document mutation crosses the interop boundary as a command and every editor-option change crosses as configuration.
- **Every mutation is a command**, whether initiated in TS (drag/connect) or C# (property edit, stencil insert): `{opId, kind, patch, resultingIds}`. Commands are validated before commit (§9.3) and pushed onto **one shared undo/redo stack, owned by TypeScript**, since most compound ops (containment/attachment cascades, waypoint edits) originate there. C#-initiated edits (property panel, stencil, import) are appended to the same TS-owned stack via interop so `Undo`/`Redo` always behaves as one linear history regardless of origin side.
- The **semantic model is the canonical truth**; JointJS cells are a rendering projection (`cell.id === bpmnElement.id`), never the reverse. This matches the spec's principle ("SVG is only a deterministic view over semantic BPMN plus BPMNDI layout").
- **Edit-mode geometry and containment behavior** are implemented in TypeScript. Pools are draggable; Pools, Lanes, and expanded embedded Sub-Processes expose outline-border resize handles; Pool/Lane bounds auto-expand during a content drag when the dragged element approaches or crosses the configured inner margin. Non-boundary Events, Activities, and Gateways at the same containment level are collision-free: creation, stencil drop, move, and resize run a geometry query against peer FlowNodes using the configured interaction-clearance inset/outset. A drag preview is constrained to the nearest valid non-colliding position; if none exists, the command is rejected and the original geometry is restored. Ancestor Pool/Lane/Sub-Process containment is not treated as a peer collision, and Boundary Event overlap with its host outline remains governed by the separate outline-lock rule. Shapes have no hard ports: connection gestures attach at arbitrary points on the target shape outline. With grid snapping disabled, the pointer is projected directly to the nearest valid outline point; with grid snapping enabled, the pointer is first snapped in paper coordinates and that snapped position is then projected to the nearest valid outline point. Grid snapping never converts the outline into fixed ports or side-midpoint anchors. Committed connections retain an editable outline attachment point. Dragging that attachment point around the outline updates the link endpoint without changing the semantic endpoint. Dragging a shape into or out of a Pool/Lane/embedded Sub-Process is a validated containment command, not an unconstrained graph move.
- **Rule duplication risk**: §5.1 (real-time) rules must exist in TS for responsiveness; §5.2+ (document-wide) rules run in C#. **Confirmed:** to avoid drift, rule IDs/tables (§5.3, §5.4) are defined once as a single **JSON rule table** (`rules/bpmn-rules.json`, checked into the repo — one entry per `SF-*`/`MF-*`/`DA-*`/`EV-*`/`GW-*`/`CT-*`/`DI-*`/`XML-*`/`EXT-*` code with `id`, `scope` (`live`/`document`), `predicate` (a small declarative expression, not free-form code, so it can be interpreted identically by both runtimes), `message`, `severity`, and `quickFix` reference). Both the TS live validator and the C# document validator consume this table at build time — TS via a static import (bundled JSON), C# via a source generator that emits strongly-typed rule classes/constants — rather than hand-duplicating the catalog in two languages. Any predicate too complex for the declarative format is implemented natively on both sides under the same rule ID, with a test asserting behavioral parity.

### JointJS OSS reuse policy

TypeScript must be an integration and BPMN-specialization layer over open-source JointJS, not a competing diagram framework:

- Reuse `dia.Graph`, `dia.Paper`, cells/views, graph batches, paper/graph events, SVG attribute binding, and native model/view lifecycle rather than implementing parallel graph, rendering, event, or batching infrastructure.
- Reuse JointJS embedding/grouping primitives (`embed`/`unembed`, parent/embedded-cell traversal, paper embedding mode/validation, graph subgraph and batch operations) for the live visual container hierarchy. Do not implement a parallel custom movement/group tree.
- Reuse JointJS geometry (`g`), anchors/connection points, routers (initially Manhattan), connectors, element/link tools, `dia.ToolsView`, and highlighters wherever they satisfy the required behavior. Wrap them behind small typed adapters so BPMN semantics and configuration do not depend on incidental JointJS object shapes.
- Build BPMN shapes by extending/composing JointJS element/link primitives and declarative SVG markup. Custom code supplies BPMN glyphs, marker combinations, semantic metadata, containment, validation, and deterministic labels; it must not replace functioning JointJS primitives merely for stylistic consistency.
- Implement custom TypeScript behavior only where open-source JointJS has no suitable primitive or where BPMN requires stronger semantics: BPMN connection/containment validation, Pool/Lane behavior, arbitrary-outline grid-snap projection, semantic copy/reference remapping, multi-diagram state, and Blazor-owned UI orchestration.
- Do not use or imitate JointJS+ APIs (`ui.*`, `shapes.bpmn2`, Halo, Inspector, Stencil, Navigator, proprietary import/export). Equivalent features must compose open-source JointJS primitives and Blazor components without copying commercial source or assets.
- Before adding a custom geometry, routing, tool, selection, or event abstraction, record which JointJS OSS primitive was evaluated and why it could not meet the contract. Keep custom layers narrow enough to replace with a JointJS primitive later.

### Blazor-owned configuration flow

- `BpmnEditor` accepts strongly typed C# configuration. Blazor merges library defaults, DI-registered options, component parameters, and host overrides; validates cross-field constraints; and produces one immutable, versioned `EditorConfig` snapshot.
- `EditorConfig` covers canvas/grid/snap, viewport, interaction tolerances and modifier keys, stencil, shared icon manifest reference/version, labels, theme/appearance, routing, selection/tools/context actions, keyboard/touch, Readonly behavior, execution overlays, accessibility, import/export, and feature flags. Configuration that affects BPMN document semantics remains a command/document edit rather than being hidden in editor configuration.
- The initial snapshot is sent through `initialize(canvasElement, document, config)` before constructing `dia.Paper`, tools, or interaction handlers. TypeScript must not briefly initialize with independent defaults and then reconfigure, avoiding visual flashes and inconsistent event binding.
- Runtime changes use `applyConfigPatch({baseRevision, revision, changes})`. TypeScript validates the contract version and base revision, applies the patch atomically, and returns an explicit success or structured rejection; stale, unknown, or internally inconsistent patches never partially apply.
- TypeScript may normalize and cache the accepted configuration for fast interaction, but cannot persist a competing preference store, silently substitute user-facing defaults, or mutate Blazor-owned configuration. JointJS options and tool instances are derived from the accepted snapshot.
- Reconfiguration distinguishes hot changes (grid visibility/size, snapping, theme, labels, shortcut bindings, tool visibility) from rebuild-required changes. A rebuild preserves semantic model, selection where valid, viewport where configured, undo/redo history, and exact BPMNDI coordinates.
- Editor configuration changes do not enter document undo/redo unless they intentionally mutate BPMN semantics or BPMNDI. Document appearance stored in DI/extensions is edited through normal commands; transient host/editor preferences are not serialized into BPMN XML.

### Edit-mode interaction contract

- **JointJS embedding is mandatory for visual containment:** `interaction/containment/` is a thin BPMN-aware adapter over JointJS embedding, not a separate hierarchy engine. It reconstructs a single-parent, acyclic visual tree from the semantic model on load and keeps it synchronized transactionally. The nearest applicable visual parent is used: plane root → Pool → nested Lane(s) → expanded embedded Sub-Process → nested content; Boundary Event → attached Activity. A content cell inside an expanded Sub-Process is parented beneath that Sub-Process even when the Sub-Process itself belongs to a Lane, preserving the complete ancestor chain. Lane embedding is visual/membership projection and never replaces Process/Sub-Process semantic ownership.
- **Links participate by scope:** Sequence Flows and local Associations/Data Associations are embedded in their lowest common rendered semantic container so explicit vertices/labels translate with it. Cross-Pool Message Flows remain graph-root cells. Link parentage is derived and cannot alter `sourceRef`/`targetRef`.
- **Groups are deliberately not containers:** a BPMN Group cell and temporary multi-selection wrapper never embed diagram cells. Moving, deleting, or resizing a Group changes only the Group; elements visually within it retain their position, semantic owner, and JointJS parent.
- **Boundary Events stick to the host Activity's outline:** a Boundary Event's shape center is always positioned exactly on its host Activity's rendered outline (rectangle perimeter, including rounded corners), never floating off it. Its position is stored as an outline-relative anchor (e.g. perimeter offset/parametric position), not an independent `(x, y)`, and is recomputed into absolute `Bounds` whenever the host moves or resizes. Dragging a Boundary Event uses the same §4.6 outline-projection pipeline (with optional grid snapping) as connector endpoints, but constrained to the host's own outline only — the pointer's nearest point on that outline is the only valid drop target; it cannot be dropped elsewhere on the canvas. Re-attaching a Boundary Event to a different host Activity is an explicit re-parent command (updates `attachedToRef`, `interaction/containment/` embedding, and the outline-relative anchor atomically) and is never an incidental side effect of an ordinary drag. Moving/resizing/rotating (Pool orientation change) the host is a single compound command that also updates every attached Boundary Event's position so it remains exactly on the new outline.
- **Non-boundary FlowNode collision enforcement:** `interaction/geometry/` exposes one typed peer-collision predicate for non-boundary Events, Activities, and Gateways. It compares effective rendered geometry at the proposed bounds plus the configured clearance across all non-ancestor peers in the active plane, including nodes in different sibling Pools or Lanes, but ignores ancestor containers and the intentional Boundary Event/host outline overlap. Stencil insertion, drag, resize, paste/clone, and semantic property edits all call the same predicate before commit and return `DI-011` with the conflicting element IDs on rejection. Imported collisions remain representable for fidelity but are surfaced as document diagnostics; import must not silently move or delete either element.
- **Sub-Process expand/collapse gestures:** a dedicated JointJS SVG selector/hit area on the collapsed `+` marker handles primary click/tap and keyboard `Enter`/`Space`, stops event propagation, and dispatches `setSubProcessExpanded(id, true)`. An expanded embedded Sub-Process collapses through double-click on its own empty body, border, or header only; the handler rejects events whose resolved JointJS view/selector belongs to descendants, links, labels, markers, tools, overlays, or HTML editors. Call Activities never participate. Edit mode records one undoable DI command updating `BPMNShape.isExpanded` and outer bounds; Readonly mode stores an instance-local transient expansion override only.
- **Expansion materialization:** expanding restores session-cached expanded bounds or deterministically fits retained child BPMNDI bounds plus configured padding/minimum size, creates/materializes descendant cells and internal links, embeds them through `interaction/containment/`, restores z-order, and reroutes in one graph batch. Collapsing first cancels nested gestures/editors and clears nested selection, then removes/hides descendant views/cells from the active paper while preserving the semantic model and child BPMNDI. External links and Boundary Events remain attached to the Sub-Process boundary. Undo/redo restores expansion state, bounds, hierarchy, visibility, selection policy, and routes exactly.
- **Pool movement:** a Pool is a draggable diagram container. Dragging its body moves the Pool and all contained Lanes, FlowNodes, Artifacts, child shapes, labels, and attached DI edges as one compound command. Dragging a Lane moves the Lane and its contents within the Pool; it cannot escape the parent Pool through ordinary movement.
- **Lane-less Pools are valid:** BPMN 2.0.2 `Semantic.xsd` makes `Participant.processRef` optional and `Process.laneSet` cardinality `0..*`. Neither black-box nor process-backed Pools require a Lane. Pool/Process creation never auto-creates a Lane; deleting the last Lane removes its `flowNodeRefs` but retains the Pool, Process, FlowNodes, and their Process ownership.
- **Resizable containers:** Pool, Lane, and expanded embedded Sub-Process views expose resize handles on their outline borders, including corners and applicable edges. Resize commands enforce minimum dimensions, header/label regions, lane adjacency, child containment, orientation, and attached-label/DI geometry. Collapsed or opaque activities are not resizable as Sub-Processes.
- **Auto-expansion:** while dragging content, the nearest eligible Pool/Lane/expanded Sub-Process expands before the content would cross its inner padding. Expansion is incremental, grid-aligned, undoable with the content move, and propagates through ancestor containers as necessary. It must not silently change Pool/Lane orientation or semantic ownership.
- **Soft outline connections with optional grid snapping:** JointJS ports are not used as BPMN semantic endpoints. A shape exposes a continuous geometric outline and valid endpoint metadata. Without grid snapping, the paper-coordinate pointer is projected directly to the nearest valid outline point. With grid snapping, the paper-coordinate pointer is snapped to the configured grid first and the snapped point is then projected to the outline; this ordering keeps the final endpoint on curved/angled outlines even when no grid intersection lies exactly on the boundary. Grid snapping must not produce a finite port set, force a side, or alter semantic endpoints. The persisted endpoint stores the resulting BPMNDI attachment waypoint, while the BPMN connector still references the shape ID.
- **Editable attachments:** each connector endpoint has an outline attachment handle in edit mode. Dragging it continuously applies the same grid-enabled or grid-disabled projection pipeline used during creation/reconnection, previews routing, and commits only after the connector-specific compatibility validator accepts the unchanged semantic endpoint pair. A configurable modifier may bypass grid snapping for the current gesture. Undo/redo restores the committed coordinate exactly rather than recalculating it under the current grid configuration. This is separate from reconnecting the connector to a different shape.
- **Manual connector dragging with routed preservation:** in edit mode, the connector stroke and its orthogonal segments are draggable. Dragging a segment creates or moves a persisted BPMNDI waypoint/vertex constraint; dragging a bend moves the corresponding vertex; dragging a label moves only the label position. In the initial release, JointJS Manhattan routing recomputes unconstrained portions of the orthogonal route while preserving explicit user constraints, connector endpoints, and BPMN semantics. The router may add, remove, or smooth intermediate bends only when doing so does not violate an explicit user waypoint/constraint. Manual routing changes are compound, undoable commands and are independent of reconnecting an endpoint.
- **BPMN-aware containment drag-and-drop:** JointJS paper embedding hit-testing identifies candidate parents and the adapter chooses the deepest eligible container. Before the final embed/unembed operation, it validates semantic ownership, Lane membership, connection scope, cycles, and parent type. On commit it updates model ownership/membership, BPMNDI, scoped-link parentage, and JointJS embedding in one graph batch/undoable command. Dragging outward is allowed only when the destination is a valid parent/root plane under §2.7–§2.8. Invalid destinations show a reason code and atomically restore the original semantic parent, embedding parent, coordinates, memberships, link hierarchy, and z-order.
- **Custom context menu only (rendered by Blazor):** the browser's native context menu is **never accessible anywhere within the editor canvas root**, in either Edit or Readonly mode. A single capture-phase TypeScript `contextmenu` handler always calls `preventDefault()` for blank paper, shapes, connectors, labels, selection/resize/link tools, and HTML editing overlays; browser context-menu behavior outside the canvas root is unaffected. TypeScript resolves the owning target and raises `contextMenuRequested`. Shape targets include their paper-relative bounding box (`x`, `y`, `width`, `height`) plus zoom/pan transform; connector targets include route bounds and nearest segment/vertex; blank-canvas requests use a zero-size paper-relative anchor at the invocation point. For an element target, the event also carries a versioned typed `BpmnElementPropertySnapshot` containing the standard semantic properties, element category/type, owner and Pool/Lane scope, references, label/DI data, capabilities, and current diagnostics; this is the binding model for the menu, not an SVG/JointJS-cell scrape or a second inferred property model. Right-click, keyboard Context Menu/`Shift+F10`, and configured touch long-press use this same path. `BpmnContextMenu` is a **child component of `BpmnCanvas`** — it is instantiated inside the canvas host's markup (overlaid via CSS above the JointJS paper, not a sibling under `BpmnEditor`), receives `contextMenuRequested` payloads directly from its parent `BpmnCanvas`, and owns positioning, edge clamping, keyboard navigation, dismissal, submenus, and action curation relative to that same canvas's bounding box. It renders standard-property editors from the snapshot and submits typed edits through the normal command channel; each response is atomic and returns the updated snapshot plus diagnostics. In Edit mode it also exposes validated **same-category type switching** (for example Service Task ↔ Message Task or None Start Event ↔ Message Start Event), preserving the element ID and compatible connections/DI while explicitly clearing or reporting incompatible properties. Cross-category switches, invalid context conversions, and Choreography/Conversation types are disabled or rejected with `DI-012`. If no target-specific actions exist, it still opens the custom canvas-level menu with applicable inspection/navigation/export actions or a disabled empty-state item; no invocation falls back to native behavior or silently produces the browser menu. Shape menus expose selection/containment/semantic/appearance actions; connector menus expose endpoint, waypoint, label/style, unlink/delete, and semantic actions. Commands return through the normal C#→TS channel and TS-owned history. Readonly menus retain inspection, copy, focus, navigation, validation, and export actions while mutation actions are hidden/disabled.
- **Selected/hovered side connector button:** built on JointJS core's `elementTools.HoverConnect` element tool (from `@joint/core`'s `elementTools` namespace) rather than a hand-rolled overlay button, matching the [`hover-element-connect-tool` demo](https://github.com/clientIO/joint-demos/blob/main/hover-element-connect-tool/js/src/main.js)'s pattern: each element view gets a `dia.ToolsView` containing a (subclassed/configured) `HoverConnect` tool, added once on element render and re-applied after any re-render, so the connect handle appears/disappears purely from JointJS's own hover/pointer lifecycle instead of custom DOM hover-tracking code. Editable shapes show this handle on hover or selection, with keyboard and pointer accessibility layered on top for parity with mouse-only demo behavior. Dragging from the handle starts a provisional link using the paper's `defaultLink`/`connectionStrategy`/`defaultConnectionPoint` (configured for arbitrary-outline pin-relative anchoring, not side-midpoint anchors) and the shared `validateConnection` hook, which delegates to the normal BPMN connector compatibility validator instead of the demo's permissive "any non-link, non-self target" check; `snapLinks`/paper-level grid-snap radius reuses the same soft-outline snapping rules as manual connector dragging (§4.6), and `linkPinning: false` keeps dangling ends impossible, consistent with §3's connection-completion requirements. The handle does not create a hard JointJS port or restrict the final attachment point: on drop, the connector snaps to the target outline and the user may later edit its outline attachment via the existing outline-attachment gesture. Boundary Events, Pools, Lanes, artifacts, and other elements that cannot initiate a given connector type hide or disable the tool according to the connector matrix (by omitting/disabling `HoverConnect` in that element's `ToolsView`, not by hiding a separately maintained custom control). The tool is removed/suppressed in Readonly mode.
- **Shared raw-SVG icon contract:** bpmn-font is an optional build-time reference, not a runtime or package dependency. The icon-generation tool may fetch or receive a pinned snapshot of the repository's raw SVG asset (for example `dist/font/bpmn.svg`), extract the named `bpmn-icon-*` glyph outlines and metadata, convert them to standalone normalized SVG paths, and commit/vendor the generated manifest (for example `icons/bpmn-icons.json`) into this library. It must not consume `dist/css/bpmn.css`, load a font, import bpmn-io packages, or require bpmn-font at application build/runtime. The manifest contains `iconId`, upstream name/codepoint, semantic element/context, generated path data, `viewBox`, baseline/alignment, accessibility label, source ref/file, and OFL 1.1 attribution. C# consumes the manifest for stencil rendering, configuration validation, property-panel/icon selection, and serialization of `iconId`; TypeScript consumes the same generated manifest for JointJS canvas shapes, stencil rendering, drag previews, and SVG export. Production rendering uses only the vendored path data. Unknown mappings, source drift, malformed SVG, or manifest-version mismatches fail generation/validation explicitly; consumers need no bpmn-io dependency or network access.
- **Stencil presentation and drag preview:** `BpmnStencil` is a vertical, data-driven stencil. Every visible stencil item renders the configured BPMN shape icon and a text label; icon geometry is resolved from the shared icon manifest and the same icon definition is used by the canvas, so stencil and canvas notation cannot drift. The stencil supports configurable item ordering, grouping/sections, visibility/curation, labels, descriptions/tooltips, icon selection/overrides by registered `iconId`, enabled/disabled state, keyboard order, and per-container availability (§9). Starting a drag creates a custom drag preview containing **only the shape icon/geometry** (never the stencil text label or surrounding stencil chrome). The preview uses the configured grid/snap scale, follows the pointer/touch point, and is converted into the normal BPMN element only after the drop passes containment and creation validation.
- **Word-wrapped labels:** every canvas label (shapes, connectors, Pools/Lanes, data/artifacts, and Text Annotations) is laid out by one deterministic TS label service using explicit `BPMNLabel.Bounds` or an element-kind default box, configured padding/font/line-height/alignment, Unicode word-boundary wrapping, grapheme-safe splitting for overlong tokens, and preserved explicit newlines. SVG output uses explicit `<tspan>` lines rather than `foreignObject` or browser-dependent auto-wrap. Inline FAST editors use the identical metrics and wrap width so commit does not reflow unexpectedly. Full semantic text is never truncated; fixed bounds may visually clip/ellipsis by configuration while accessibility/tooltips/property inspection retain the complete string.
- **Multi-Process/Diagram navigation:** a `Definitions` document may contain multiple `BPMNDiagram`/`BPMNPlane` elements over multiple `Process`/`Collaboration` root elements (e.g. a Collaboration plane plus a separate plane per called/global Process). The editor treats this as a navigable document, not a single fixed canvas. Blazor's document/diagram manager owns the list of diagrams/planes (create/rename/delete/duplicate/reorder) and the **currently active plane**; switching planes tells TypeScript to `loadDocument`/swap the active `dia.Graph` (or an isolated sub-graph view) while keeping the rest of the in-memory semantic model resident, so undo/redo history, execution-state overlays, and unsaved edits on other planes are preserved across a switch. Navigation entry points, all reference-driven and validated against the document model before switching:
  - **Diagram/plane picker:** a toolbar/tab or tree control listing every `BPMNDiagram` (label, owning Process/Collaboration, participant count) for direct selection.
  - **Call Activity drill-down:** double-click or a context-menu/side-panel "Open called process" action on a Call Activity navigates to the `BPMNDiagram` for its `calledElement` Process, if one exists in the document; if the referenced Process has no diagram/is external, the action is disabled with a reason (e.g. "no local diagram", "unresolved reference") instead of failing silently.
  - **Expanded vs. reusable Sub-Process distinction:** expanded/embedded Sub-Processes remain drawn in place (per §2 embedded-vs-reusable rules) and are not part of this cross-diagram navigation; only Call Activities and reusable global Processes participate, since they always resolve to a separate root Process element/diagram.
  - **Breadcrumb trail (consumer-rendered):** the component library does **not** own or render breadcrumb UI itself. Each successful diagram/plane switch — whether via the picker, Call Activity drill-down, or reference-browser navigation — updates an internal navigation path/stack (root → ... → current plane, each entry carrying diagram ID, label, owning Process/Collaboration, and the triggering Call Activity ID when applicable) and raises a `diagramNavigated` event containing the full path plus the switch's origin (`picker` | `drillDown` | `back` | `referenceBrowser`). The **editor's parent/host application** is responsible for building and rendering any breadcrumb UI in response to that event, including jump-back-to-ancestor behavior (which the host implements by calling `setActiveDiagram(pathEntry.diagramId)` again) and reset/branch semantics when navigating directly via the picker. `BpmnDiagramNavigator.razor` supplies only the diagram/plane picker (list/tree + selection), not a breadcrumb widget; a host may optionally reuse the emitted path data to build its own breadcrumb component, but the library ships no default breadcrumb rendering.
  - **Reference browser integration:** the existing reference browser/"find usages" surface (§3.2) can navigate directly to the owning diagram of any found reference, and safe-rename/duplicate-ID-repair operations remain correct across all diagrams in the document, not just the active one.
  - **Cross-diagram integrity:** deleting or renaming a Process/Collaboration that owns a diagram other planes reference (via `calledElement` or Participant `processRef`) requires the same transactional reference-update/rejection behavior as other reference edits (§3.2); it is never silently limited to the active plane.
  - Readonly mode retains full diagram/plane navigation, drill-down, and `diagramNavigated` events for host-rendered breadcrumb use — none of this is gated behind edit mode.

#### 3.1.1 Detailed designs for Gap/Partial items

Each item below elaborates the corresponding table row into a concrete design: owning module, commands/interop, data contract, edge cases, and Readonly behavior. All commands are TS-owned undo/redo entries unless stated otherwise; all are hidden or disabled (never silently no-op) in Readonly mode.

- **Multi-selection / bulk selection and pool-scoped selection (Gap) — `interaction/selection/`.** Rectangular (rubber-band) and additive lasso selection start on empty-canvas pointerdown/drag; `Shift`/`Ctrl`/`Cmd`+click toggles individual cells; `Ctrl+A`/configurable shortcut selects all cells on the active plane. Selection is **pool-scoped by default**: a rubber-band drag starting inside a Pool/Lane only selects descendants of that container unless a configurable modifier extends it to siblings/cross-pool. Selection state is a TS-owned `Set<cellId>` broadcast via the coalesced `selectionChanged` event (ids, kinds, and a computed "capability summary" — e.g. `canGroupMove`, `canDelete`, `canClone` — so the property panel/toolbar can react without re-deriving BPMN rules). Group operations (move, delete, clone) run through the containment/connection validators per-element and are wrapped in one compound command; if any member of the group would produce an invalid result (e.g. moving a Lane's Lane out of its parent Pool), the entire compound command is rejected atomically with an aggregated reason list, never partially applied. Bulk property edits (§3.2 Inspector) apply only to the common editable fields across the heterogeneous selection.
- **Delete, clone, copy/paste, cut, select-all, escape/cancel (Gap) — `interaction/clipboard/`.** A command-based, in-memory (not OS clipboard, to avoid cross-tab BPMN-XML leakage risk — configurable to opt into OS clipboard as plain BPMN-XML fragment) clipboard holds a serialized sub-graph: BPMN semantic elements, DI, and internal connector waypoints for the current selection, expanded to include contained children (Pool/Lane/Sub-Process content) and to exclude dangling connectors whose other endpoint is outside the copied set (dangling ends are dropped with a diagnostic, not silently kept invalid). `Cut` = copy + delete as one compound command. `Paste`: all IDs are regenerated, all internal references (sequence flow refs, `flowNodeRef`, `calledElement`/`processRef` that point *inside* the copied set) are remapped consistently, references to elements *outside* the copied set are preserved as-is (e.g. pasting a Call Activity keeps pointing at the same external global Process). Paste position defaults to a small cursor-relative offset from the copy origin, or the current pointer/drop location on paste-at-target; paste validates containment/connection rules before commit and rejects atomically (with reason codes) rather than partially pasting. `Escape` cancels the active gesture (drag, connect, resize, rubber-band, inline edit) without mutating the model; it never has to be a clipboard action per se, but shares the same keyboard-map plumbing. Readonly mode permits copy (as an export/inspection action) but not cut/paste/delete.
- **Halo-like contextual actions and quick-add/quick-link (Gap) — `interaction/contextual-actions/`.** A small custom TS overlay (HTML, not `foreignObject`, consistent with the inline-editing overlay strategy) appears anchored to a selected shape's outline, distinct from both the right-button context menu (§2) and the side connector button (§2): it surfaces the highest-frequency actions as icon buttons (remove, clone, replace, quick-add-connected-element, unlink) so users are not forced through a menu for common operations. "Quick-add": clicking a directional quick-add affordance creates a new, stencil-default-configured element of a compatible type (per the connection matrices) in the indicated direction, auto-connects it with a valid connector type, and auto-positions/auto-expands the parent container as needed — implemented as one compound command so a single undo removes both the new shape and its connector. "Quick-link": dragging from the affordance behaves like the side connector button (§2) but is available as part of this same overlay rather than a separate control; the two may share the same underlying `connect-button` gesture implementation. The whole overlay is configurable (which actions appear, ordering) via the same curation mechanism as the stencil, and is suppressed entirely in Readonly mode (falls back to the read-only right-click menu for inspection-only actions).
- **Shape replacement and context-menu type switching (Gap) — `interaction/contextual-actions/replace.ts` + C# `SemanticEditing/`.** The context menu and contextual actions use one schema-driven replacement command. Its picker is filtered to registered BPMN types in the same element category and valid context: a Task may switch to Service Task, Message Task, User Task, or another eligible Activity subtype; a None Start Event may switch to Message Start Event or another valid Start-event definition; a Gateway may switch only among compatible Gateway types. Cross-category conversions (such as Task → Gateway or Start Event → End Event) and excluded Choreography/Conversation types are never offered. The command preserves the element ID, compatible connections and references, containment/embedding, label, position/size where valid, compatible extension fields, and DI. It clears or reports incompatible standard properties (for example removing an obsolete timer/message definition) through explicit `Info`/`Degraded` diagnostics, validates the complete post-conversion graph, and commits as one undoable atomic command; any `DI-012`, connection, containment, collision, or semantic failure restores the original element exactly.
- **Link tools: endpoint editing, vertices, segment/bend manipulation, remove, label editing (Partially covered) — `interaction/link-tools/`.** Builds directly on the already-specified manual connector dragging/outline-attachment/waypoint model (§2) by adding the discoverable **tool affordances** JointJS+ demos show on hover/selection of a link: small icon buttons at the link's midpoint and at each vertex for "remove connector", "add vertex here", "remove this vertex", and "edit label"; a source/target endpoint marker that is draggable (reusing the outline-attachment drag, not a new mechanism) with visual valid/invalid target feedback during the drag (shared with tooltip/target-aim feedback below). "Remove connector" is a single command that also cleans up any now-dangling label/DI; it is different from the connector-specific right-click "unlink/delete" menu action — both exist and invoke the same underlying command. All link-tool affordances are hidden and inert in Readonly mode, where only label/property **inspection** remains via selection.
- **Inline label editor (Partial) — `interaction/link-tools/` (connector labels), `interaction/semantic-editing/` (shape labels), and shared TS `labels/`, rendered via the existing HTML-overlay-over-SVG pattern.** This is the **only** surface that ever commits label text; there is no popup window, browser `prompt()`/modal dialog, or separate floating editor anywhere in the product for this purpose. Invocation: double-click on a shape/connector label, `F2`/configurable keyboard shortcut on a selected element, or the context-menu/link-tool "edit label" action — all three converge on this same in-place overlay, never a distinct dialog. The FAST text-input/textarea is positioned and sized from the current label's effective bounds and paper transform, pre-filled with the complete semantic text, and uses the exact same font metrics, padding, Unicode word/grapheme wrapping, explicit-newline handling, alignment, and width as the committed SVG `<tspan>` layout. It may grow vertically up to a configurable maximum but must not change semantic geometry implicitly. `Enter` (or blur, configurable) commits as a single property-edit command; `Escape` cancels and restores the prior value without mutating the model. Label position (for connectors, a draggable offset along/off the route) is a separate gesture from text editing. In Readonly mode, double-click/`F2` shows the label in the read-only property panel field for inspection only (not an editable popup); no editable surface, inline or otherwise, is ever shown.
- **Inspector/property editor with content and appearance tabs (Partial) — `BpmnPropertyPanel.razor` + C# `SemanticEditing/`.** The existing schema-driven, contextual/conditional property panel (§ Required Features, §3.2) is extended with a second, always-present **Appearance** tab/section alongside the semantic **Content** tab: fill/stroke color (constrained to the active theme's token palette, §Gap below, plus an "custom color" escape hatch that is flagged in validation as a non-standard/vendor-extension appearance override so it round-trips through `Bpmn.Interchange` extension preservation rather than being silently dropped), text/font style for labels, connector line style/width/dash pattern (kept distinct from the BPMN-semantic connector *type*, which determines marker/dash by rule — appearance overrides are additive, never allowed to change what marker a Sequence/Message/Association/Data-Association connector renders, since that would violate §4 marker rules), and a "reset to theme default" action per field. Multi-selection bulk edit shows only the fields common to every selected element/connector kind and (per BPMN-2.0.2 field) either the shared value (if identical across the selection) or a "mixed values" placeholder; committing an edit in mixed-value state applies the same command to every selected element as one compound operation. Appearance fields are DI-level (or a documented vendor extension where DI has no native field) and never affect BPMN semantic validity.
- **Toolbar, zoom, fit-to-viewport, print, SVG/image export (Partial) — `BpmnToolbar.razor` (commands) + TS `viewport/` and a new `export/` module.** Explicit toolbar commands: zoom in/out/to-percentage/reset, fit-to-content (with configurable padding), fit-to-selection, pan-mode toggle, undo/redo, validate-now, and export. **Print**: a dedicated print stylesheet/print view renders the current plane (or selection, or whole document across multiple planes as separate pages when configured) at print-appropriate scale/pagination, with overlays (inline-edit widgets, contextual-action affordances, connector-button) torn down beforehand — the exact same teardown step used for SVG export, so the two share one "prepare for external rendering" routine. **SVG export**: serializes the live SVG DOM after overlay teardown, re-inlines any CSS custom properties/theme tokens needed for the SVG to render correctly outside the app, and optionally embeds execution-state overlays only when explicitly requested (default excluded, since execution state is ephemeral/host-supplied and usually undesired in a static export). **Raster export** (PNG/JPEG) rasterizes the prepared SVG at a configurable DPI/scale via canvas draw, reusing the same teardown. **Selection-only export** clips/crops to the selection's bounding box (with configurable padding) instead of the full plane. All export/print actions are available in Readonly mode; none require edit mode.
- **File import overlay and import diagnostics (Partial) — `BpmnImportDialog.razor` (Blazor UI) over the existing C# `Serialization/` import pipeline.** Adds the missing UI shell around the already-specified `Bpmn.Interchange`-based reader: a file-picker/drag-and-drop target, an upload/parse progress indicator, a **preview** step that parses and validates the incoming document into a detached in-memory model *before* touching the live graph (so the current diagram is never mutated by a failed or partial import), a diagnostics list surfaced from `Bpmn.Interchange`'s `Info`/`Degraded`/`Dropped` results plus this library's own structural validation (§5.2–§5.5) run against the preview model, and explicit **Cancel** (discards the preview, no change) vs **Commit** (atomically replaces/merges the live document — configurable to import as a new diagram/plane into the current document rather than always replacing it wholesale) actions. A failed parse (malformed XML, unsupported schema version) shows the diagnostic and blocks Commit; a degraded-but-parseable import (e.g. dropped vendor extensions) still allows Commit but requires the diagnostics list to have been shown, not silently commit clean. This dialog is available in Readonly mode only if the host explicitly enables "import to inspect" (default: import requires edit mode, since Commit is a mutation).
- **Keyboard shortcuts and shortcut help dialog (Partial) — `keyboard/` (TS map + dispatcher) + `BpmnShortcutHelp.razor`.** The existing configurable keyboard map (`setKeyboardMap(config)`) is given documented, overridable **defaults** covering: delete, undo/redo, copy/cut/paste, duplicate/clone, select-all, escape/cancel, zoom in/out/reset/fit, pan (space+drag or arrow keys), print, quick-add (when a shape is selected, in a configurable direction), and diagram/plane navigation (next/previous, breadcrumb-back — dispatched as host-level events per the earlier "host-rendered breadcrumb" decision, not a library-owned action). A `?`/configurable "show shortcuts" action opens a searchable, read-only help dialog listing the active (possibly host-customized) bindings grouped by category; it reads live from the same keyboard-map config so it never drifts from actual bindings. Shortcut conflicts with the host page/browser (e.g. `Ctrl+P`) are documented as configurable-away, not silently overridden. The help dialog and all shortcuts that only navigate/inspect remain available in Readonly mode; mutating shortcuts (delete, paste, etc.) are inert (not merely hidden from the help list — explicitly listed as "disabled in Readonly mode").
- **Tooltips, hover/target-aim feedback, link-snap feedback (Partial) — `interaction/` cross-cutting, surfaced through the HTML-overlay pattern for rich tooltips and through SVG class/attribute toggles for lightweight per-shape highlighting.** Configurable tooltips (content, delay, enable/disable per element kind) appear on hover for stencil items (name/description, already partly specified in §9), canvas shapes (semantic summary — e.g. element type, key properties), and toolbar/contextual-action buttons (accessible name/description, doubling as the `title`/`aria-label` source so tooltip text and accessibility text never diverge). During a connect/quick-link/side-button drag, candidate drop targets are evaluated live against the connector compatibility matrices and outline-snap tolerance: valid targets get a highlighted outline and a "snap point" indicator at the projected outline location; invalid targets get a distinct "not-allowed" visual state and, on hover-pause or on drop, a short reason string (reusing the same rule-table reason codes as commit-time validation, so hover feedback and final rejection messages are always consistent). This feedback layer is purely visual/non-mutating and remains fully active in Readonly mode wherever hover/inspection is otherwise allowed; only the drag-to-connect gesture itself is Readonly-suppressed.
- **Color palette, themes, dark mode, contrast checks (Gap) — new `theming/` (TS, CSS custom-property token set consumed by both JointJS shape styles and FAST component theme) + Blazor `BpmnThemeProvider`.** A configurable theme is a named set of design tokens (surface/background, shape fill/stroke per BPMN category, selection/hover/invalid-target colors, execution-state status colors — kept in a palette visually distinct from semantic appearance colors so the two families never collide — text, focus ring, and high-contrast variants), shipped with at least a light and dark built-in theme and an explicit high-contrast profile. Tokens are exposed as CSS custom properties so FAST chrome (stencil, panels, menus, toolbar) and the JointJS-rendered SVG shapes (via attribute/class bindings, not hard-coded colors) stay visually consistent and swap atomically on theme change, with no flash-of-unstyled-shape. A build-time/dev-time contrast-check utility validates every semantic-color-on-background and execution-status-color-on-background pairing in every shipped theme against WCAG AA text/non-text contrast minimums (feeding into the M7 automated accessibility checks) and flags any host-supplied custom theme/appearance override (from the Inspector's Appearance tab) that fails the same contrast check, without blocking its use (a warning, not a hard rule, since some appearance overrides are intentionally decorative). Theme selection (including dark mode) is a host-facing configuration option and works identically in Readonly mode.

1. Use a **central visual token model** shared by FAST chrome and SVG, with light/dark/high-contrast profiles.
2. Use geometry-following selection outlines, translucent selected-link halos, lightweight Pool previews, Lane insertion guides, and purple dashed provisional links as configurable defaults.
3. Keep the stencil compact but do **not** copy its icon-only design; the confirmed requirement is icon + text.
4. Preserve explicit differences from the demo: zero-Lane Pools, arbitrary outline anchors with optional grid snapping, shape+connector+canvas custom menus, resizable expanded Sub-Processes, no minimap, and full semantic property editing.
5. Treat demo source as behavior/reference evidence only. Do not copy `@joint/plus` shape markup, private package implementation, proprietary icons, or token-gated import/export logic.

The feature-parity audit above covers general diagram-editor ergonomics. This audit checks whether the plan exposes editing workflows for every important in-scope BPMN 2.0.2 semantic family from the base specification. Rendering an icon or preserving XML is not sufficient: each editable semantic choice must be reachable through a validated property editor, creation action, or reference-management workflow.

#### 3.2.1 Detailed designs for Gap/Partial items

Each item below elaborates the corresponding §3.2 table row into a concrete design: owning module (C# `SemanticEditing/`/`Model/` unless noted, plus any TS counterpart), data-model/interop shape, validation touch-points, and Readonly behavior. All edits are property/creation commands that flow through the standard C#→TS command channel and land in the single TS-owned undo/redo history; every editor validates against §5 rules and the shared `rules/bpmn-rules.json` table before commit, and every editor is read-only (fields shown, disabled) rather than hidden in Readonly mode unless stated otherwise.

- **Definitions, target namespace, imports, multiple Processes/Collaborations/Diagrams, root-plane selection (Partial) — `SemanticEditing/DocumentManager` (C#) + TS `diagram-nav/`.** A `BpmnDocumentManager` inspector/panel exposes: `Definitions` metadata (`id`, `targetNamespace`, `exporter`/`exporterVersion` shown read-only), an `Imports` list (add/remove `wsdl`/`xsd`/`bpmn` imports with `namespace`/`location`/`importType`, each validated for resolvability where the target is itself a known document), and a root-element manager listing every `Process`/`Collaboration`/`GlobalTask` with create/rename/duplicate/delete. Deleting a root element that is referenced (by a Participant's `processRef`, a Call Activity's `calledElement`, or another diagram's plane) is blocked with a "N references would break" diagnostic and an option to first navigate to and fix each reference (reusing the reference browser, §3.2 "Global references" below) rather than silently cascading deletes. Duplicating a Process/Collaboration deep-copies its content and regenerates all internal IDs (same remap approach as clipboard paste) while duplicating the owning `BPMNDiagram`/plane so the copy is immediately viewable. The already-specified multi-diagram picker, Call Activity drill-down, and `diagramNavigated` event (§2) are the navigation half of this capability; this item is the authoring half (create/rename/delete/duplicate/import management). Fully available for inspection in Readonly mode; mutation actions are disabled.
- **Pools/Participants and `processRef` / black-box Pools (Partial) — `SemanticEditing/Participants` (C#).** Pool selection surfaces a Participant inspector with: `name`, a `processRef` picker restricted to Process root elements not already exclusively bound to a different single-instance Participant (multiple Participants may reference the same Process only where that is semantically meaningful, e.g. multi-instance-like collaboration patterns — configurable strictness), and a **black-box toggle**. Switching a process-backed Pool to black-box hides (does not delete) its FlowNode/Lane content — content is retained in the model, marked non-visible on the active plane's DI, and restored unchanged if the user switches back to process-backed, so no data loss occurs from a round trip. Switching a black-box Pool to process-backed either attaches an existing Process (via the `processRef` picker, keeping that Process's own diagram/content intact and simply rendering it inside the Pool) or creates a new empty Process. Participant bounds (position/size) are the existing Pool resize contract (§2); this item is the `processRef`/black-box semantic layer on top of it. All fields are Readonly-inspectable.
- **Lanes/LaneSets and nested lane hierarchy (Partial) — `SemanticEditing/LaneSets` (C#), TS `interaction/containment/`.** The Lane-set editor supports adding/removing/reordering top-level and nested Lanes and displays each Lane's `flowNodeRef` membership. Horizontal/vertical Pool orientation constrains Lane layout; splitting/merging preserves membership. Removing the final Lane is legal and retains all Process-owned FlowNodes. Fully Readonly-inspectable.
- **Start/Intermediate/Boundary/End Event definitions (Partial) — `SemanticEditing/EventDefinitions` (C#) + TS `shapes/` marker sync.** Selecting any Event shows an event-definition editor: a type picker limited to definitions valid for that Event's category/position (Start: none/Message/Timer/Conditional/Signal/Escalation/Compensation/Error — the last only for Event Sub-Process Start Events per §2 rules — Multiple/Parallel Multiple as containers of the above; Boundary: adds Cancel and enforces interrupting-vs-non-interrupting exclusivity per definition type; End: adds Error/Escalation/Compensation/Cancel/Terminate/Signal/Message as throw semantics only, never catch-only definitions like Timer/Conditional), and per-definition-type fields (Message: message-catalog picker; Timer: date/duration/cycle expression + language; Conditional: condition expression + language + evaluation-variable reference; Signal/Error/Escalation: catalog picker with "create new" inline; Link: paired throw/catch name with a same-Process pairing validator that flags unmatched Links; Compensation: activity-to-compensate reference, Boundary-only). Changing event-definition type re-renders the shape's marker glyph (§4) immediately through the same shared icon/marker contract, and is a single undoable command. Catch/throw legality, interrupting/non-interrupting toggling (Boundary only), and scope (e.g. Escalation/Error propagation target) are validated against §2/§5 before commit. Fully Readonly-inspectable.
- **Activity markers and execution behavior (Partial) — `SemanticEditing/ActivityCharacteristics` (C#) + TS marker rendering.** An "Execution behavior" property group on any Activity (Task/Sub-Process/Call Activity) exposes mutually-aware fields: loop type (none / standard loop / multi-instance), standard-loop fields (loop condition expression + language, maximum-iterations, test-before/after), multi-instance fields (sequential vs. parallel, loop cardinality expression, `loopDataInputRef`/`loopDataOutputRef` with data-object pickers, input/output data-item mappings, completion-condition expression), compensation flag (marks the activity as a compensation handler, only legal attached via a Compensation boundary/association per §2), ad-hoc ordering (only on Ad-Hoc Sub-Process: sequential/parallel indicator, completion condition, cancel-remaining-instances flag), and transaction method (Transaction Sub-Process only: cancel/compensate/none end-event method mapping). Selecting an invalid combination for the activity's current type (e.g. transaction method on a plain Task) hides those fields rather than showing a disabled/invalid state, since they are not applicable, not merely unavailable. Every field change re-renders the corresponding marker glyph(s) (loop/parallel-MI/sequential-MI/ad-hoc/compensation) via the shared icon contract as one undoable command. Fully Readonly-inspectable.
- **Embedded/event Sub-Processes, Transactions, Call Activities, reusable global Processes/Tasks (Partial) — `SemanticEditing/SubProcessConversion` (C#) + TS containment.** A "Convert to..." contextual/context-menu action on a Task or (embedded/collapsed) Sub-Process offers only semantically legal targets: Task ⇄ embedded Sub-Process (expanded, empty) ⇄ collapsed Sub-Process (same element, DI-only expand/collapse toggle, content preserved either way) ⇄ Event Sub-Process (adds the "no incoming/outgoing Sequence Flow at the Sub-Process boundary" constraint and requires exactly one triggering Start Event with an event definition once content exists) ⇄ Transaction (adds the transaction-method field above and the standard/cancel/compensation End Event legality constraints) ⇄ Call Activity (prompts for an existing global Process via `calledElement` picker or "create new global Process from this Sub-Process's current content", which extracts the content into a new root Process/diagram and replaces the Sub-Process with a reference, as one compound, undoable, reference-safe command — the inverse "inline this Call Activity's called Process" extraction is also offered where the called Process has no other referrers). Invalid conversions (e.g. Task directly to Transaction without an intermediate Sub-Process state) are excluded from the offered list, not attempted and rejected. Boundary Events and any content already attached remain correctly re-owned by the conversion. Fully Readonly-inspectable (current kind and its fields are visible; the convert action itself is edit-mode-only).
- **Task-specific implementation metadata (Partial) — `SemanticEditing/TaskMetadata` (C#).** Each Task subtype gets a dedicated metadata group in the property panel, shown only for the matching subtype: User Task (assignee/candidate-users/candidate-groups as extension or engine-specific fields, form reference); Manual Task (description only — no implementation fields, by spec); Service Task (`implementation` string or `operationRef` picker into the global Interface/Operation catalog, mutually exclusive); Script Task (script body editor + `scriptFormat` language picker); Business Rule Task (`implementation`, optional decision reference as extension); Send/Receive Task (`messageRef` picker into the Message catalog, `operationRef` picker, and for Receive Task the `instantiate` flag). All Task subtypes additionally get an input/output data-mapping editor (Data Input/Output Associations, item-aware, sharing the Data Association editor described below). Fields with no engine-portable BPMN-core representation are explicitly modeled as configurable extension fields (never invented as fake core attributes) and round-trip through `Bpmn.Interchange` extension preservation. Fully Readonly-inspectable.
- **Messages, Signals, Errors, Escalations, ItemDefinitions, CorrelationProperties (Gap) — `SemanticEditing/GlobalCatalog` (C#), a new `BpmnGlobalCatalogPanel.razor`.** A document-scoped catalog panel lists each global definition family (Messages, Signals, Errors, Escalations, ItemDefinitions, CorrelationProperties) with create/rename/edit/delete/"find usages" per entry. Fields per type: Message (`name`, optional `itemRef` to an ItemDefinition); Signal (`name`); Error (`name`, `errorCode`, optional `structureRef`); Escalation (`name`, `escalationCode`); ItemDefinition (`structureRef`, `isCollection`, `itemKind`); CorrelationProperty (`name`, `type`, correlation-property-retrieval-expressions per Process). Deleting an entry with existing usages is blocked with a navigable usage list (reusing the reference browser) rather than a silent cascade; renaming updates the definition's `id`/`name` and is safe by construction since all referencing pickers store the ID, not a copied name. Every event-definition, message-flow, and data picker elsewhere in the editor (Event Definitions, Task metadata, Message Flow inspector, Data Object/ItemDefinition fields) sources its options from this same catalog, so there is exactly one authoring surface per global family. Fully Readonly-inspectable (browse/find-usages available; create/edit/delete are edit-mode-only).
- **Interfaces, Operations, Resources, ResourceParameters, InputSets, OutputSets, Properties (Gap) — `SemanticEditing/ServiceCatalog` (C#), extends `BpmnGlobalCatalogPanel.razor`.** Adds a second catalog section for service-oriented definitions: Interface (`name`, `implementationRef`) containing Operations (`name`, `inMessageRef`/`outMessageRef` pickers into the Message catalog, optional error refs), Resource/ResourceParameter (`name`, `type`) for Resource Role assignment on Activities/Lanes, and Property (`name`, `itemSubjectRef`) plus InputSet/OutputSet definitions used by data mappings and multi-instance loop data. Service/Send/Receive/Call Task inspectors (above) and Data Association editors (below) consume this catalog through reference pickers rather than free-text, and an "unresolved reference" diagnostic (surfaced in `BpmnValidationPanel`, §5) flags any stored reference whose target has since been deleted or was imported but not resolvable, blocking export until resolved or explicitly acknowledged. Fully Readonly-inspectable.
- **Data Objects, Data Object References, Data Stores, Data Store References, Properties (Partial) — `SemanticEditing/DataObjects` (C#) + stencil distinction (§9).** The stencil/creation action distinguishes creating a **Data Object definition** (document-scoped, `itemSubjectRef`, `isCollection`) from dropping a **Data Object Reference** or **Data Store Reference** onto the diagram (diagram-scoped, `dataObjectRef`/`dataStoreRef` pointing at a definition or document-scoped Data Store respectively) — the same underlying definition may have many References across one or more diagrams, each with independent DI position. The inspector for a Reference exposes its target-definition picker (with "create new definition" inline) plus its own `name` override; the inspector for the definition itself exposes `itemSubjectRef`/`isCollection`/`state` (a free-text or enumerated data-object state label per spec). Data Store additionally has `capacity`/`isUnlimited` at the document-scoped Data Store level. Fully Readonly-inspectable.
- **Sequence Flow conditions, default flows, Message Flow metadata, Association/Data Association metadata (Partial) — `SemanticEditing/ConnectorMetadata` (C#) + TS `link-tools/`.** Sequence Flow inspector: condition expression + language (only enabled when the source is a Gateway or an Activity with multiple outgoing flows, per §2/§3 rules — otherwise hidden as inapplicable), and a "set as default flow" action that is mutually exclusive with a condition on the same source (setting one clears the other, with a confirmation if the flow already has a condition) and enforces at most one default flow per source. Message Flow inspector: `messageRef` picker (Message catalog), and read-only display of the enforced different-Pool endpoint rule. Association inspector: `associationDirection` (none/one/both) and, for Data Associations specifically, the transformation expression + language and the direction-derived legality of source/target types (Data Object/Store Reference ⇄ Activity/Throw-catch-capable node) per the Data Association matrix (§3). Every connector inspector field change is validated against the connector-specific compatibility matrices and rule table before commit, consistent with the existing link-tools/manual-routing commands. Connector labels (name display) reuse the inline label editor (§3.1.1). Fully Readonly-inspectable.
- **Groups, Text Annotations, Associations, compensation associations, artifacts (Partial) — `SemanticEditing/Artifacts` (C#) + TS `shapes/`.** Group: creation by selecting a region (auto-computed bounding categorization box, not owning tokens or containment semantics — a Group is DI/visual only) or explicit stencil drop, with a `categoryValueRef` picker (creating category values inline) and resize/move like any artifact. Text Annotation: free-text content editor (multiline, reuses the inline label/overlay editor pattern) with configurable max length and an Association endpoint to the annotated element. Association: source/target endpoints restricted to legal artifact-to-flow-element pairs per §3's Association matrix, with `associationDirection` shared with the metadata item above. Compensation Association: a specialized Association variant automatically implied when a Compensation boundary event is connected to its compensation-handler activity — modeled as a derived/read-only relationship in the inspector (not independently createable) to avoid divergence from the Boundary-Event-driven compensation model (§2). All artifacts are explicitly validated as non-token-flow (never accepted as Sequence Flow endpoints). Fully Readonly-inspectable, including Text Annotation content.
- **Collaboration messages/correlation and cross-Pool editing (Partial) — `SemanticEditing/Collaboration` (C#) + TS connection validator.** At the Collaboration/plane level, a "Message Flows" panel lists all Message Flows with participant-aware endpoint pickers (source/target restricted to FlowNodes belonging to *different* Participants, or a black-box Participant itself when its content is hidden) and `messageRef` selection from the global Message catalog (reusing the picker from "Messages..." above). Correlation is modeled via CorrelationProperty retrieval expressions attached per-Process (edited in the global catalog item above) plus, where used, a CorrelationKey grouping editable from this same Collaboration panel. When a Participant toggles from black-box to process-backed (or vice versa, per the Pool item above), every Message Flow referencing that Participant is preserved by ID/endpoint-participant-reference, not by FlowNode, so the flow survives even though its concrete visual endpoint may need re-anchoring to a specific FlowNode inside the now-visible content (prompted as a one-time "attach to a specific flow node" action, defaulting to the Participant boundary if left unattached, which remains valid). Fully Readonly-inspectable.
- **Global references used by Call Activities and hidden semantic elements (Partial) — `SemanticEditing/ReferenceBrowser` (C#), a new `BpmnReferenceBrowser.razor`.** A dedicated panel lists every reference-bearing relationship in the document (Call Activity → global Process, Participant → Process, Sequence/Message Flow → source/target, Data Association → Data Object/Store, event definitions → Message/Signal/Error/Escalation, extension-preserved references) with a search/filter box and "find usages" invoked from any element's context menu or the global catalog entries above. Selecting a usage navigates to its owning diagram (via the same `diagramNavigated` mechanism as Call Activity drill-down, §2) and selects/highlights the referencing element. **Safe rename**: renaming any referenceable definition's display `name` never breaks references (which are ID-based), but renaming/changing an `id` itself (only offered as an explicit "change ID" advanced action, since IDs are otherwise stable and system-generated) runs a transactional update of every reference to the old ID as one compound command, or is blocked with the full usage list if any reference is in a currently-unloaded diagram the tool cannot safely rewrite. **Duplicate ID repair**: on import or paste, if two elements would share an ID, the diagnostics pipeline reports it and offers one-click regeneration of the later element's ID plus all its own outgoing references (not incoming ones, which by definition point at the *other*, surviving ID). **Hidden-definition preservation**: global definitions not currently visualized on any diagram (e.g. an orphaned Message never yet used) are retained in the document model and listed in the global catalog panel above rather than being pruned on save/export. Fully Readonly-inspectable (browse/find-usages/navigate; rename/repair are edit-mode-only).
- **Engine extensions and extension definitions (editing gap) — `SemanticEditing/Extensions` (C#) + shared extension schema config.** Beyond the already-specified content-lossless passthrough (unknown vendor `extensionElements`/attributes preserved byte-for-byte through `Bpmn.Interchange`), this item adds an **extension-aware editing surface**: a host-supplied, versioned extension-field schema (analogous in shape to the icon manifest — `extensionId`, owning BPMN element types, field list with type/validation/label) lets a consuming application register known vendor/engine extension fields (e.g. a specific workflow engine's retry policy on a Service Task) so they render as normal typed property-panel fields instead of raw XML, while any extension content *not* covered by the registered schema still round-trips untouched and unedited. Editing a known extension field is a standard property command, validated by the field's declared type/rules, and never weakens or bypasses BPMN-core structural validation (§5) — an extension cannot make an otherwise-invalid core structure valid. Unregistered/unknown extension content is shown in a read-only "raw extension" inspector view (for visibility/debugging) in both edit and Readonly modes; only registered fields become editable, and only in edit mode.

## 5. Interop Contract (sketch, for validation)

- **Direction TS → Blazor**: batched, coalesced events — `selectionChanged`, `commandApplied` (for undo/redo + property panel sync), `validationRequested`, `contextMenuRequested` (target kind/id; paper-relative anchor bounds `{x, y, width, height}` plus zoom/pan transform; connector nearest segment/vertex where applicable; blank canvas uses a zero-size anchor at the invocation point; mode and valid actions; Blazor owns all menu rendering), `diagramNavigated` (full root-to-current path and navigation origin for host-owned breadcrumb rendering). The canvas-root capture handler has already suppressed the native browser menu before `contextMenuRequested`; there is no fallback path that enables it. Never send per-pixel drag events. Every one of these events is received exclusively as a `[JSInvokable]` method on `BpmnCanvasEventBridge` (one method per TS event name, 1:1, no generic/untyped dispatch method); `BpmnCanvasEventBridge` is instantiated and owned by `BpmnCanvas`, passed to TS as the `DotNetObjectReference` target at `initialize(...)` time, and re-raises each call as a strongly typed .NET event/callback that `BpmnCanvas` exposes to its parent (`BpmnEditor`) and children (e.g. `BpmnContextMenu`). No other C# type may hold a `DotNetObjectReference` into this module or receive these callbacks directly.
- **Direction Blazor → TS**: **initialization, commands, configuration, and state updates** — `initialize(canvasElement, document, editorConfig)`, `applyPatch(command)`, `applyConfigPatch(configPatch)`, `loadDocument(model)`, `setActiveDiagram(diagramId)` (swaps the active `dia.Graph`/plane view while retaining other planes' undo/redo history and unsaved edits in the resident semantic model), `setExecutionState(executionState)`, `clearExecutionState()`, `requestExport()`, `focusElement(id)`. `EditorConfig` is the authoritative aggregate contract; stencil, icons, keyboard, Readonly, grid/snap, routing, theme, tools, and interaction options are sections of its snapshot/patch rather than independently owned TS settings. `StencilConfig` includes vertical layout, ordered/groups, item visibility, labels, descriptions/tooltips, icon selection/override by shared `iconId`, enabled state, keyboard order, and per-container availability. Icon-manifest compatibility and every config patch are version/revision checked and rejected atomically on failure. Blazor never pushes raw DOM/SVG instructions or raw JointJS option objects. Every one of these calls is issued exclusively through `BpmnCanvas`'s own `IJSObjectReference`; sibling/ancestor components never import the JS module or call it directly — they invoke a method/event on `BpmnCanvas` (e.g. `BpmnStencil` raises a "drop" callback that `BpmnCanvas` translates into `applyPatch`), keeping exactly one component responsible for the module's lifetime and its interop surface.
- All interop payloads are versioned contracts distinct from the internal TS/C# model shapes, so either side's internal representation can evolve independently — this avoids the common Blazor-JS-interop trap of interop code depending on internal model layout.
- **Direction TS → Blazor configuration acknowledgement**: `initialized({configRevision})` and `configApplied({revision, rebuildPerformed})`, or `configRejected({revision, code, path, message})`. Configuration failures are explicit and leave the last accepted snapshot active. These, too, are `BpmnCanvasEventBridge` `[JSInvokable]` methods, not ad hoc callbacks.
- All access to `_content/Hasseware.AspNetCore.Components.Bpmn/Hasseware.AspNetCore.Components.Bpmn.lib.module.js` is centralized in `BpmnCanvas`: it is the only component that calls `IJSRuntime.InvokeAsync<IJSObjectReference>("import", ...)` against that module path, the only component that holds the resulting `IJSObjectReference`, and the only component that constructs/disposes the `DotNetObjectReference<BpmnCanvasEventBridge>` passed into it. The module reference is loaded once per `BpmnCanvas` instance (on first render / `OnAfterRenderAsync(firstRender: true)`) and disposed, along with `BpmnCanvasEventBridge`'s `DotNetObjectReference`, in `BpmnCanvas.DisposeAsync`, matching the Fluent UI Charts pattern. `BpmnEditor` and every other component (`BpmnStencil`, `BpmnPropertyPanel`, `BpmnToolbar`, `BpmnDiagramNavigator`, `BpmnValidationPanel`, `BpmnContextMenu`) only ever talk to the canvas module indirectly through `BpmnCanvas`'s C# API (method calls in, .NET events out) — never by resolving or caching their own reference to the JS module.

### Naming Conventions & Guidance:
- **No `Dto` / `DTO` Suffix**: Do NOT use `Dto` or `DTO` in any model, contract, class, or interface name across both C# and TypeScript codebases.
- **Domain-Centric Naming**: Use clean, descriptive domain terms instead (e.g. `ExecutionState`, `ActivityStatus`, `CommandPayload`, `StencilConfig`, `ValidationDiagnostic`, `BpmnDocument`).

### Code quality, refactoring, and language policy

- **Clean code is an acceptance criterion.** Blazor/C# and TypeScript changes must be cohesive, readable, testable, and free of avoidable duplication before a feature is complete. Passing tests does not justify retaining unclear structure, oversized modules, duplicated rules, leaky abstractions, or dead code.
- **Refactor continuously.** Refactor when responsibilities blur, branching or nesting becomes difficult to reason about, the same behavior appears twice, a JointJS/interop concern leaks into domain code, or a feature would otherwise require a workaround. Refactoring directly coupled to a feature belongs in the same change and retains behavior through focused tests; do not postpone necessary cleanup to an unspecified later phase.
- **Prefer the latest stable language features supported by the pinned toolchain.** The .NET/Blazor project uses the latest stable C# language version available for its target framework; TypeScript uses the latest stable compiler syntax supported by the pinned build toolchain. Prefer modern syntax when it improves correctness or clarity. Preview/experimental language features require an explicit project decision and must not be enabled implicitly.
- **C# guidance:** enable nullable reference types, implicit/global usings where appropriate, collection expressions, primary constructors, records/read-only record structs for value-like immutable contracts, required members, property/list patterns, switch expressions, file-scoped namespaces, async streams, `await using`, and spans/value-oriented APIs where they make code clearer and measurably appropriate. Prefer immutable public contracts and cancellation-aware async APIs. Avoid reflection-heavy mapping, service location, sync-over-async, mutable global state, and allocations disguised by unnecessarily clever LINQ in interaction hot paths.
- **TypeScript guidance:** enable the strictest practical compiler checks (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, and unused-code checks); prefer `satisfies`, discriminated unions, exhaustive `never` checks, type-only imports, readonly data, private fields where useful, optional chaining/nullish coalescing, async/await, and modern ECMAScript modules. Avoid `any`, unsafe double assertions, numeric/string enum dependence where literal unions fit, prototype mutation, namespace-style modules, and untyped JointJS/interop payloads.
- **Boundaries remain explicit:** domain rules, JointJS adapters, Blazor components, serialization, interop contracts, and presentation helpers have separate responsibilities. UI components orchestrate rather than contain validation/serialization logic; JointJS views do not become the semantic model; interop modules translate contracts rather than expose internal objects.
- **Small, purposeful APIs:** prefer composition and focused functions/classes over inheritance hierarchies, except where extending a JointJS primitive is the idiomatic integration point. Keep public surface area minimal, remove obsolete members during controlled breaking-version changes, and document only non-obvious invariants or compatibility decisions.
- **One source for each rule or configuration.** Generate or share rule IDs, icons, and interop schemas where practical. Do not copy constants, defaults, marker paths, or compatibility matrices between C# and TypeScript.
- **Automated quality gates:** builds treat compiler/analyzer/linter warnings as errors for maintained source, with narrowly documented suppressions. C# uses repository-standard formatting and analyzers; TypeScript uses formatting plus type-aware linting. CI runs format verification, C# build/analyzers, TypeScript type-check/lint, unit tests, and relevant contract/API compatibility checks.
- **Refactor safety:** behavioral refactors must preserve focused unit, snapshot, interop-contract, and E2E coverage. Performance-sensitive interaction code is benchmarked/profiled before and after a substantial structural change; readability must not be traded for speculative micro-optimization.

## 7. Open Questions Requiring Your Confirmation

1. **~~State ownership / undo-redo stack owner~~** — **CONFIRMED**: TS-owns-graph, C#-owns-document-lifecycle hybrid per §2; the single undo/redo stack is **TypeScript-owned**, with C#-initiated edits appended to it via interop.
2. **~~XML import/export location~~** — **CONFIRMED (backend revised 2026-09-19)**: XML import/export stays on the **Blazor/C# side**, but implemented by this library rather than on top of `Bpmn.Interchange`, whose measured round-trip loses artifacts, data references and valid-but-not-executable events and leaves orphaned DI behind (see §3 and `docs/interchange-spike.md`). The §6 editor data model in `Model/` is the semantic model of record; the reader maps XML straight onto it, so no adapter layer to a third-party object model is needed.
3. **JointJS open-source constraint** — confirmed: use JointJS open source only; JointJS+ and commercial plugins are not available. The initial M0–M7 delivery uses JointJS core Manhattan routing plus custom OSS-compatible BPMN shapes, tools, and inspectors.
   - Reuse open-source JointJS primitives wherever they satisfy the contract; custom TypeScript is limited to BPMN semantics and capabilities genuinely absent from JointJS OSS.
   - Blazor is authoritative for editor configuration; TypeScript derives JointJS options and custom behavior from versioned Blazor configuration snapshots/patches.
4. **~~In-canvas HTML overlay strategy~~** — **CONFIRMED**: HTML-overlay-over-SVG (not `foreignObject`) for FAST-component-based inline editing widgets, TS-owned, synchronized to the paper viewport transform and removed before SVG export.
5. **~~Shared rule-table format~~** — **CONFIRMED**: a single JSON rule table (`rules/bpmn-rules.json`) consumed by both the TS and C# validators (static import in TS, source-generated in C#), instead of maintaining §5's rule catalog by hand in two languages.
6. **~~Accessibility scope for v1~~** — **CONFIRMED**: M3 ships only the base a11y skeleton; full keyboard graph navigation + ARIA tree is phased into M7.
7. **~~Workflow Execution State schema & presentation preference~~** — **CONFIRMED**: execution state schema is `ExecutionState { instanceId, elements: [{ elementId, status, tokenCount, incidents }], flows: [{ flowId, traversed, traversalCount }] }`. Animated sequence-flow token paths are a desired feature but are **optional, off by default**, toggled via an `ExecutionAnimation` configuration setting; static traversal highlighting is the default presentation.
8. **~~Readonly Mode behavior~~** — **CONFIRMED**: Readonly mode still allows element selection and property inspection via a read-only property panel; only mutation-capable interactions (drag/resize/reconnect, stencil, editing context-menu actions) are disabled.
